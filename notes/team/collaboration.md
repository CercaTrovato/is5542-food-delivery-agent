# 组内协作规范

接手任务时先读[当前方案与进度](../current-plan.md)，再从[首页分工](../../README.md#首轮实名分工)打开自己的任务卡。各人的 Agent 也按这个顺序读取。涉及此前交件时，使用交件人提供的文件路径和提交号，必要时回读原始证据。

## 派任务时给什么

| 字段 | 写法 |
|---|---|
| 任务和接收人 | 用一个稳定名称或编号，写清谁负责、交给谁。 |
| 目标和范围 | 说明要解决哪个问题或验证哪个场景，例如 P02 恰好到阈值时怎么判。 |
| 输入与版本 | 列来源文件、提交号或规则版本、可用的数据和前置依赖。缺失的输入标待核。 |
| 输出和完成标准 | 说清交件路径、格式、验收者和能据此核对的结果。 |
| 日期和确认状态 | 标香港时间，区分建议日期与成员已确认的日期。 |

接收人用一句话复述「我接什么、预计交什么、现在缺什么」。如果缺一个关键输入，说明它阻塞哪一步，以及哪些部分可以先做。

## 交结果时给什么

每次在交件文件、PR 或进度留言里保留以下短记录，原始材料只放一次。

~~~text
任务／负责人／接收人：
状态：准备中、待复核、已验收或阻塞
完成了什么：
输入版本：代码提交、规则版本、用例或来源
交件位置：仓库路径、PR 或证据链接
如何核对：复跑命令、场景、预期和实际结果
待核／阻塞：缺什么，影响哪一步，谁来补
下一步：
~~~

- **待复核**表示交件已放到指定位置，接收人可以检查。**已验收**表示接收人按完成标准核过。
- 竞品材料分开写公开条款、实际观察和推断。缺证据的条目写待核。工程与测试标明使用演示规则还是团队已确认规则。
- 改动共同的业务规则、角色分工或正式日期前，把问题、选项和影响带回组内确认。确认后更新[当前方案与进度](../current-plan.md)，各自再更新受影响的任务卡或交件。
- 代码或文档用各自分支协作。交接引用具体提交和路径，避免同一文件在多个 Agent 手里各自成为一份最新版。

例如，P02 的记录可以写「使用演示规则，恰好 30 分钟，预期直接结束。提交号为实际版本，运行结果附截图或日志。正式阈值待团队确认」。其他成员读完就知道这次试跑证明了什么。
