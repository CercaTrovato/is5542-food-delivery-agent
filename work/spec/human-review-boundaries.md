# 人工重审与改额规则（human-review-v1）

**本人于2026-11-23逐项确认了以下四项。规则已确认；本批只发布规范，未修改或验证当前网页代码。** 生效验收组合为既有`demo-v1`＋`human-review-v1`，开发提交与运行记录需明确二者。正式对照B/C共用同一执行边界，不能一边放松权限来制造差距。

## 四项规则，用人话说

| 项 | 已确认的做法 |
|---|---|
| 什么情况允许重审 | 原申请已经驳回且没有成功发过补偿；顾客补了影响判断且能核实的新信息，或客服发现之前判断／记录／规则使用错误。人工写明原因，沿用原工单核对。仅反复不满意而没有新信息时继续解释，不重开。 |
| 谁能改金额 | 只有主管角色R002能修改金额。普通客服R001按标准金额处理，需要改额交主管；R003只读，顾客和AI不能直接修改。系统角色不改变小组分工。 |
| 金额怎么限制 | 标准10元模拟券；主管可改为1—20元整数，且不得超过订单实付金额，每次改额写原因。20元是课程演示上限，不代表平台统一规定。 |
| 怎么防重复 | 同一订单最多成功补偿一次。重审沿用原工单／补偿记录；发过后不再重审改额或补差价。连点、刷新、重试、换客服／会话都返回原状态，不再发一份；不同订单独立。 |

重审是重新核对，仍需按事实和适用规则决定。保留原驳回及后续操作记录，不能用覆盖原原因来掩盖历史。**本轮不增加发券后的补差价、撤销、追回或真实退款系统，也不增加新的审批层级。**

## 与既有规则、旧决定怎样衔接

- 已送达且延误严格超过30分钟、顾客确认后提交、人工审批，是既有`demo-v1`验证基准。本次改的是重审／金额／发放边界，不授权绕过订单归属、未送达条件或基础资格。
- D15记录11/21只补原因＋人工入口的最小范围，D16记录11/22考虑扩展方向；本次D17总项及D18—D21确认四个细项。当前以本文件为准，旧决定保留历史，不继续把重审写成一律禁止。
- 普通客服可按标准金额处理；自定义金额必须走主管权限，不能通过改请求、普通审批入口、人工咨询入口、创建工单或补资料入口绕过。
- 所有实际发放都受实付上限约束。标准10元超出实付时不自动改金额，交主管在已定范围内处理；实付缺失、不可核或不存在合法正整数金额时先阻止发放，核清再处理。
- 不新增“最多重审几次”等未确认的次数规则；但只有未成功补偿且有上述理由才可重审。防重复按订单身份累计，换聊天／人工编号／规则版本不能清零已补记录。

## 给开发：只对齐现有功能，不重做系统

1. 用服务端核验的账号、角色、订单归属和实付金额；不要接受顾客聊天自报金额或浏览器传入角色作为权限依据。
2. 在现有重开入口检查原状态、未补偿标记和原因。是否存在新信息／原处理错误由人工判断并写明，AI不能自动替人工重开。
3. 所有可能批准／发放的入口共用金额和角色检查，包含直接工单审批、人工咨询处理、主管改额及旧入口。无权限、空原因、越界、小数等应拒绝，不能悄悄截断或钳成合法金额。
4. 发放前检查同一订单的成功／处理中记录；在一次原子状态更新中确认并写入成功结果。重复请求返回现有状态。不能只靠按钮变灰，也不能仅按工单号／规则版本去重。
5. 记录订单、原工单、操作人／角色、时间、旧状态／金额、新状态／金额、重审／改额原因及发放结果。复用现有数据库与流水，不为本轮引入新支付基础设施。

现有分支曾支持更宽的重开／金额操作，不等于已经满足本规范。交件列“已对齐／未对齐”、实际提交、线上对应版本、模型／配置及原始复测证据。既有8行试用通过不能自动认证这些新边界。

## 给测试：只补受影响的边界

按[九组边界复测](../eval/human-review-boundary-checks.md)留证；不重做所有旧用例。技术部分由测试组协作，gaga仍只做轻量视觉与提示是否清楚。旧失败、旧报告和新结果分开保留；新规则未实际复测前不写“已上线／已通过”。

本人四次确认的顺序为：重审条件→改额权限→金额范围→防重复。全都来自本课程会话的本人直接答复；不是开发自测、自动勾选或平台资料代替本人决策。
