## 两边共同保留什么

真实同一模型及参数、同一数据与demo-v1、同一登录身份／商户权限、同一有权限的查单工具、多轮上下文、顾客确认、工单持久化、人工审批及结果回显。共同执行层不得放松权限、允许聊天改金额／审批或未确认发券。可复用同一前端和LangGraph框架，不开发第二套网站。

基础B流程：顾客问题→模型理解／追问→调用查单工具→模型按规则给资格与下一步→顾客确认→同一工单／人工审批→结果回显。缺资料回追问，无权／查无记录说明原因。不能只写提示词称自己会查工具，必须有真实调用与后端动作。

## 主要判断差别与已披露的附带差异

| 位置 | B：基础工具型 | C：显式业务规则型 |
|---|---|---|
| 身份、合法订单事实、工具、上下文 | 共用 | 共用 |
| 时间与延误事实 | 同工具提供相同时间字段和同一算法算出的延误秒数，不预塞正确资格答案 | 相同 |
| 资格／需要追问或人工等下一步 | 模型读相同业务规则，输出结构化建议；不暗中调用C资格函数代答 | 程序规则节点给建议 |
| 确认、工单、人工审批、最终执行安全检查 | 共用 | 共用 |
| 日志与评价 | 同样保留决策建议、兜底前后回答／动作、最终状态及模型调用 | 相同 |

这比较“业务决策由模型判断还是由显式规则处理”，不是证明LangGraph品牌优于另一框架。B本身也可用LangGraph。若实际仍有其他差异，必须列出来，不能静默多改因素。不能把全租户订单表交给B而只给C合法事实；同样不能把预期资格／答案藏进模型上下文。

## 输出及失败如何处理

建议用共同字段表达资格、下一步和理由，服务端分别保存“原始建议”和“最后实际动作”。格式错、模型失败、被共同安全层挡住都记录；不能自动退回模拟模型并继续计真实样本。B给错建议但后端拦住，应分别记录决策错误和执行被拦，不能只按终态把两者都算完全正确。自然语言表达用共同格式／处理，金额和状态安全检查保持一致。

模型调用次数不必硬凑相同，因为这是实际成本／效率的一部分；分别记每次系统实验、底层模型调用、Token、耗时、错误／重试。重复试验不得拿缓存同一次结果冒充独立调用。基础B额外实现时间由开发先回报，不能把本文写成已经支持的启动参数。
